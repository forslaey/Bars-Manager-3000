# Реальный отклик служб BARS — исследование 21.10.2026

## Что возможно

Да, менеджер может периодически проверять реальный отклик конкретной службы и предлагать перезапуск при устойчивом сбое. Для этого нужна проверка, которую выполняет сама служба: диагностический HTTP/API-запрос, безопасный запрос по её протоколу или поддерживаемый разработчиком сигнал прогресса. Универсального внешнего способа доказать зависание любой службы Windows нет.

Текущий менеджер обновляет состояние Service Control Manager каждые 10 секунд, пока модуль открыт. В `ServiceCore.cs` перечисляются службы через `EnumServicesStatusEx`. Из нативного статуса сохраняются состояние и возможность остановки; PID, коды выхода, CheckPoint и WaitHint пока не передаются в модель `ServiceEntry`. HTTP-проверок отклика, анализа событий Windows и отдельного фонового монитора сейчас нет. Изменениями этого этапа они не добавлялись.

`Running` сообщает о состоянии, заявленном службой Windows, а не о прохождении её рабочих запросов. Microsoft отдельно документирует CheckPoint/WaitHint для длительных переходов запуска, остановки, паузы и продолжения. Их отсутствие прогресса может указывать на сбой перехода, но эти поля не являются проверкой обработки запросов в состоянии Running. [SERVICE_STATUS_PROCESS](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_status_process).

## Как использовать Swagger без знания программирования

Swagger показывает описание API: адреса методов, параметры, авторизацию и ответы. Это не встроенная гарантия исправности. [Методы и пути в OpenAPI](https://swagger.io/docs/specification/v3_0/paths-and-operations/), [описание ответов](https://swagger.io/docs/specification/v3_0/describing-responses/).

1. Открыть уже известную страницу Swagger нужной службы в браузере. Не угадывать порты и не сканировать рабочую сеть.
2. Найти методы с названиями `health`, `ready`, `live`, `ping` или `status`. Это примеры названий, а не подтверждённые методы BARS.
3. Прочитать описание: что проверяет метод, требует ли параметры/авторизацию и какой ответ считается нормальным. Даже GET нельзя считать безопасным только по названию. Команды создания/удаления, синхронизации, кассовых операций и прочих изменений для мониторинга не подходят.
4. Сначала передать адрес Swagger либо описание метода для разбора. Секреты, пароли и токены не присылать. Выполнять запрос через «Try it out» только после подтверждения, что он диагностический и не меняет данные.
5. Для выбранного метода согласовать URL, ожидаемый код и содержимое ответа, нормальное время выполнения, авторизацию и время прогрева после запуска. HTTP 200 без проверки смысла ответа недостаточен. Автоматические перенаправления на страницу входа не должны считаться успехом.

У конкретных служб BARS адреса и контракты в этом исследовании не получены; пользователь сообщил о Swagger у части служб. Ни один API BARS не вызывался.

## Что проверять

| Сигнал | Что позволяет утверждать | Чего не доказывает |
|---|---|---|
| Состояние SCM, время проверки | Windows считает службу запущенной/остановленной | Что рабочие запросы выполняются |
| CheckPoint/WaitHint во время перехода | Есть ли прогресс запуска/остановки | Исправность уже запущенной службы |
| Проверка TCP-порта | Соединение принято | Исправность обработчика и зависимостей |
| Открытие Swagger, ответ version/ping | Отвечает конкретная точка входа | Работоспособность базы, очереди и основной функции |
| Согласованный диагностический запрос | Выполнена именно эта проверка с ожидаемым результатом | Полную исправность всех операций |
| События Windows и логи | Дополнительные факты о сбое | Что ошибка относится к текущему зависанию; отсутствие ошибок не доказывает исправность |
| CPU/память и время изменения файла | Косвенные признаки активности | Что служба зависла либо исправна |

Microsoft различает liveness (жизнеспособность процесса) и readiness (готовность обслуживать запросы). Сбой зависимости может сделать службу неготовой без необходимости её перезапуска. Поэтому нельзя одинаково перезапускать службу при тайм-ауте, недоступной базе, ошибке сертификата и неверной авторизации. [Health checks in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/health-checks?view=aspnetcore-10.0).

## Предлагаемое поведение будущего монитора

Это проект следующего этапа, а не уже реализованная функция.

- Отдельно показывать состояние Windows и результат проверки отклика, вместе со временем последней проверки. Например: «Запущена; отвечает за 120 мс» либо «Запущена; три запроса подряд завершились по тайм-ауту».
- При отсутствии профиля писать «Проверка отклика не настроена». При проблемах доступа, TLS или авторизации писать конкретную причину; не объявлять службу зависшей.
- Выполнять проверки асинхронно, с ограничением параллелизма и размера ответа, без наложения запросов одной службы. После закрытия модуля отменять запросы. Явно объяснить, работает ли монитор только в открытом модуле; постоянный монитор потребует отдельного решения.
- Настраивать интервал, тайм-аут, число последовательных сбоев и время прогрева по конкретной службе. Стартовый пример для обсуждения: интервал 15 секунд, тайм-аут 3 секунды, предупреждение после 3 сбоев; это не проверенные значения для BARS.
- После устойчивого сбоя показывать «Нет подтверждённого отклика» и кнопку предложения перезапуска с причиной, временем и результатами последних проверок. Не писать «Зависла» без подтверждения. Не повторять одно предупреждение на каждом цикле; снимать его при восстановлении.
- Перезапуск выполнять только после подтверждения пользователя, повторной проверки выбранной регистрации и действующего состояния. Остановить конкретную службу, дождаться остановки, запустить и после прогрева проверить отклик. Если остановка зависла, показать ошибку, а не убивать процесс по имени. Учесть зависимости и возможный общий процесс нескольких служб.
- Собирать только нужные диагностические сведения; не писать токены, пароли и полный ответ с рабочими данными в журнал. Не отключать проверку TLS ради прохождения теста.

Для рабочего проекта профилей достаточно сначала получить адрес Swagger одной службы и определить один безопасный метод. Если подходящего метода нет, потребуется помощь разработчика службы. Само наличие Swagger позволяет исследовать API, но не гарантирует возможность надёжной проверки зависания.

## Границы проверки

Изучены текущий код SCM и официальные материалы Microsoft/Swagger. Реальные службы не запускались, не останавливались и не перезапускались. Запросы к API BARS, анализ реальных логов и проверка гипотез о зависании не выполнялись. Инструкция в программе содержит отдельный раздел с простым объяснением Swagger и этих ограничений.
